# ADR-012: PostgreSQL as the sole source of truth (no cached balance)

## Status

Accepted

## Context

`ACC-003` explicitly allows a cached balance for performance but states it "cannot replace ledger as source of truth." `docs/ARCHITECTURE.md` §4 similarly notes "a future cached balance table may be introduced only with reconciliation tests." `NFR-003` requires no correctness-critical state to live only in process memory, to support horizontal API replicas.

## Decision

Do not store a running balance column anywhere. `financial_accounts.initial_balance` plus a SQL-time aggregation over `transaction_entries` (`AccountBalance`/`LiquidBalance` in `postgres/store.go`) is computed fresh on every read. No in-memory cache of balances exists in the API process.

## Consequences

### Positive
- Impossible for a cached balance to drift from the ledger — there is nothing to reconcile because there is no second copy of the truth.
- Horizontal scaling is trivial for this data path — any API replica gets the same answer directly from Postgres, no cache-invalidation coordination needed between replicas.
- Simplifies reversal semantics enormously — reversing a transaction "just works" for balance purposes since the balance query already nets out every entry, including the offsetting reversal entries.

### Negative
- Every balance read is an aggregation query rather than an indexed point-lookup — for accounts with a very large number of entries, this could become a performance concern (`NFR-002` targets P95 <300ms for simple reads; this hasn't been load-tested against high transaction-count accounts).

### Risks
- If a cached balance is introduced later (as the architecture doc anticipates as a possibility), it must ship with reconciliation tests per the doc's own explicit caveat — skipping that would reintroduce the exact class of bug this design currently avoids.
