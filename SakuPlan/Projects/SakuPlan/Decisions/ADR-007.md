# ADR-007: Immutable reversal instead of mutation or deletion

## Status

Accepted

## Context

PRD §7.1 ("Ledger first") requires financial history to be append-oriented and auditable; `BR-004` requires a reversed transaction to have zero net impact while both the original and its reversal remain visible in audit history. `TXN-006` forbids direct account-balance editing.

## Decision

Corrections are made by creating a **new** transaction of type `reversal`, linked to the original via `reverses_id`/`reversed_by_id` (self-referential FKs on `financial_transactions`), with entries that offset the original's entries exactly. The original row is never mutated or deleted. A transaction can be reversed exactly once — reversing a reversal, or a transaction that already has `reversed_by_id` set, returns `ErrConflict`.

## Consequences

### Positive
- Full audit trail is preserved automatically — no separate audit log entry is needed to reconstruct "what happened and when it was corrected."
- Balance reconstruction (`initial_balance + Σ entries`) naturally nets out reversed transactions without special-casing.
- Idempotent — reversing with the same `Idempotency-Key` twice returns the same reversal, doesn't double-reverse.

### Negative
- No "edit and replace" semantics (PRD `TXN-008` describes "reversal-and-replacement" as a `SHOULD`, but only reversal is implemented — replacement, i.e. automatically creating a corrected transaction linked to the reversal, is not implemented).
- Reports that don't explicitly exclude reversed transactions' original impact could double-count unless they respect `reversed_by_id` — no dedicated report exists yet to verify this is handled correctly end-to-end (see [[Reports API]]).

### Risks
- None identified beyond the above — this is a low-risk, well-tested decision (`TestReverseTransactionRestoresBalanceAndIsIdempotent`, `TestReverseTransactionRejectsSecondReversal`).
