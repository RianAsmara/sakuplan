# ADR-009: OpenAPI-first client contract

## Status

Accepted

## Context

Mobile (React Native + Expo) and admin web (Next.js) clients don't exist yet, but PRD §10 states both are intended to use an OpenAPI-generated TypeScript client rather than hand-written HTTP calls, to keep request/response shapes in sync with the backend without manual duplication.

## Decision

Maintain `services/api/openapi/openapi.yaml` (OpenAPI 3.1.0) as the API contract, hand-authored alongside the Go handlers (not generated from Go code). `docs/PRD.md` §10 designates this file as canonical for the exact contract.

## Consequences

### Positive
- Contract is inspectable and versionable independent of the Go implementation.
- Once mobile/admin-web work begins, client code generation can start immediately from this file.

### Negative
- Hand-authored spec can drift from the actual handler behavior — one confirmed drift already exists: `CreateBillRequest.frequency` is restricted to `[monthly]` in the spec, matching the current `BillService` restriction, but neither matches the domain enum (`weekly`/`monthly`/`yearly`) or the PRD requirement (`BILL-002`) — see [[Bills API]].
- No CI step validates the spec against actual handler behavior (no contract-testing job in `.github/workflows/backend.yml`) — see [[CI and Quality Gates]].

### Risks
- Without automated drift detection, the spec's accuracy depends entirely on manual discipline as new endpoints are added.
