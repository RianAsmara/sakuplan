# ADR-003: Clean Architecture dependency boundaries

## Status

Accepted

## Context

Financial business rules (ledger, budgets, safe-to-spend) must remain testable without a database or HTTP server, and must not accidentally depend on framework details that could silently change monetary behavior. `CLAUDE.md` makes this a hard rule: domain/application packages must not import Fiber, pgx, Fx, JWT libraries, or environment configuration.

## Decision

Structure the codebase as four layers with dependency direction pointing strictly inward: Transport (`internal/adapters/httpapi`) → Application (`internal/application`) → Domain (`internal/domain` + `internal/ports`) ← Infrastructure (`internal/adapters/postgres`, `security`, `system`). Domain declares interfaces (`domain.XxxRepository`, `ports.Xxx`); infrastructure implements them; application depends only on the interfaces, never the concrete adapters.

## Decision (verification)

Confirmed by direct inspection: `internal/application`'s files import only `context`, stdlib packages, and `internal/domain`/`internal/ports` — zero framework imports found across all application files.

## Consequences

### Positive
- `internal/application` services are unit-testable with fakes, no Fx/Fiber/pgx required — enables the fast test layer described in [[Testing Strategy]].
- Swapping infrastructure (e.g. Postgres → another driver, HS256 → asymmetric JWT signing per `docs/ARCHITECTURE.md` §6) doesn't require touching business logic.

### Negative
- More ceremony than a framework-coupled "fat handler" style — every use case needs an interface plus at least one adapter implementation.
- No automated lint rule currently enforces the import boundary — it's a convention, verified manually in this synchronization pass, not machine-checked.

### Risks
- Without an import-boundary linter (e.g. `depguard`), a future contributor could accidentally import Fiber into `internal/application` and nothing in CI would catch it.
