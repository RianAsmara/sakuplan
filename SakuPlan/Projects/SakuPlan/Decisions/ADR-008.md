# ADR-008: Integer minor-unit money representation

## Status

Accepted

## Context

Floating-point arithmetic cannot exactly represent all decimal currency amounts and accumulates rounding error across many operations — unacceptable for a financial ledger. `BR-001`/`CLAUDE.md` mandate integer minor units; `TXN-002` requires rejecting floating-point monetary input entirely.

## Decision

Represent all monetary values as `domain.Money`, a named `int64` type in minor units (e.g. IDR `100000` = Rp100.000 — IDR has zero decimal minor units in this MVP). Every monetary database column is `bigint`. JSON request/response bodies carry money as integers, never floats.

## Consequences

### Positive
- Exact arithmetic everywhere — no rounding error in balance reconstruction, budget validation, or recommendation allocation.
- Overflow is the only failure mode to guard against (not precision loss), and it's handled explicitly — see `addNonNegativeMoney`/`proportionalMoney` in [[Financial Invariants]].

### Negative
- `domain.Money.Add`/`Sub` methods don't themselves guard against overflow or negative results — that protection lives separately in `internal/application/money_math.go`. Raw `+`/`-` on `Money` values elsewhere (e.g. in `PlanningService.SafeToSpend`) bypasses even those helpers, relying on the caller to reason about bounds.
- `NewMoney(v int64)` (the constructor with a negative-value guard) is defined but not actually called anywhere in the reviewed application code — validation is redone ad hoc per input field instead of centralized through the constructor.

### Risks
- The multi-currency requirement is explicitly deferred (P1 scope) — introducing it later will require deciding how minor-unit-per-currency (e.g. USD cents vs. IDR whole units) is represented without breaking this invariant.
