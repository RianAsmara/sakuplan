# ADR-005: pgx v5 with explicit SQL over an ORM

## Status

Accepted

## Context

Financial correctness depends on precise control over SQL — transaction boundaries, exclusion constraints (`budget_periods_no_overlapping_active`), CTE-based atomic operations (refresh-token rotation), and exact ledger-balance aggregation. PRD §21 fixes the driver as pgx v5.

## Decision

Use `github.com/jackc/pgx/v5` / `pgxpool` directly with hand-written SQL in a single `postgres.Store` type (`internal/adapters/postgres/store.go`), rather than an ORM or query builder. Thin `XxxRepo` types wrap `*Store` and implement the `domain.XxxRepository` interfaces.

## Consequences

### Positive
- Full control over transaction semantics — `Store.WithinTransaction` implements `ports.UnitOfWork` directly, with nested-transaction-safety via a context-stored `pgx.Tx`.
- Complex invariants (the `EXCLUDE USING gist` budget-overlap constraint, the atomic refresh-token-rotation CTE) are expressed exactly, not fought through an ORM abstraction.
- Centralized Postgres-error-to-domain-error translation (`mapError`) keeps error handling consistent across all repositories.

### Negative
- More boilerplate per query than an ORM/query-builder would require.
- SQL correctness relies on manual review and integration tests (`tests/integration/postgres_test.go`) rather than compile-time schema checking.

### Risks
- `internal/adapters/postgres` has 0% unit-test coverage (per [[Test Coverage]]) — it's covered only by the single integration test, which does not exercise every repository method (e.g. no dedicated integration coverage of auth/session rotation or reversal against real Postgres).
