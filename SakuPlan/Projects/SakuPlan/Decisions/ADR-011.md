# ADR-011: Refresh-token rotation with family revocation

## Status

Accepted

## Context

`AUTH-003`/`SEC-002` require refresh tokens to be opaque, stored only as hashes, rotated on every use, and require that reuse of an already-rotated token revoke the related token family — a standard defense against refresh-token theft (an attacker who steals and replays an old token should not be able to silently ride along with the legitimate session).

## Decision

Generate refresh tokens as 256-bit random values (`crypto/rand`), store only their SHA-256 hash (`refresh_sessions.token_hash`, unique). Every login starts a new `family_id`; every successful rotation carries the same `family_id` forward and marks the previous session `revoked_at` + `replaced_by_id` via a single atomic Postgres CTE (`RotateSession`, using `FOR UPDATE` to serialize concurrent rotation attempts). If a session that's already been rotated (has both `revoked_at` and `replaced_by_id` set) is presented again, the entire family is revoked via `RevokeFamily`.

## Consequences

### Positive
- A stolen-and-replayed refresh token, once the legitimate client has already rotated past it, invalidates the whole session chain rather than just the one token — limiting the blast radius of token theft.
- The rotation itself is race-safe: concurrent refresh attempts on the same token are serialized by `FOR UPDATE`, with the loser getting `ErrConflict` rather than silently issuing two valid successor tokens.

### Negative
- A legitimate client that retries a refresh call after a network blip (without waiting for the response) could trigger a false-positive reuse-detection and get its whole family revoked, forcing a fresh login. This trade-off isn't independently tested against a genuine retry scenario in the current test suite (`TestRefreshRotatesSessionAndRejectsReuse` only tests the deliberate-reuse case).

### Risks
- None beyond the retry false-positive above — the core mechanism is well-tested and matches an industry-standard rotation pattern.
