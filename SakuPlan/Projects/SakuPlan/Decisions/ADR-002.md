# ADR-002: Modular monolith instead of microservices

## Status

Accepted

## Context

SakuPlan's domain (identity, accounts, ledger, budgets, bills, goals, planning) is highly interdependent — most operations touch the ledger, and budget/safe-to-spend calculations read across several modules in a single request. PRD §18 explicitly lists "premature microservice decomposition" as out of scope, and `docs/ARCHITECTURE.md` §1 describes the chosen style as "a modular monolith using clean architecture boundaries."

## Decision

Ship one deployable Go service (`api`, single binary `cmd/api`) with internal package boundaries (`internal/domain`, `internal/application`, `internal/adapters`, `internal/bootstrap`) enforcing separation without network boundaries between modules. A future `cmd/worker` (see [[Background Jobs]]) is planned to share the same `internal/application` packages rather than duplicating logic across services.

## Consequences

### Positive
- No distributed-transaction complexity for ledger writes — a budget activation or transaction reversal is a single Postgres transaction, not a saga across services.
- Lower operational overhead for an MVP-stage product: one deploy artifact, one database, no service mesh.
- `NFR-003` (horizontal API replicas, no correctness-critical in-memory state) is still satisfiable — PostgreSQL is the sole source of truth (see [[ADR-012]]), so the monolith can scale horizontally without sharing in-process state.

### Negative
- All modules share a failure domain — a bug in one handler can, in principle, affect the whole process (mitigated by `recover` middleware).
- Independent scaling of hot paths (e.g. safe-to-spend reads vs. ledger writes) isn't possible without splitting the monolith later.

### Risks
- If a future `cmd/worker` process is added without discipline, shared `internal/application` packages could accumulate transport-specific assumptions that make the split harder later.
