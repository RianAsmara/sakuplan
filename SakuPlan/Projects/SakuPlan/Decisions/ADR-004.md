# ADR-004: Uber Fx restricted to the composition root

## Status

Accepted

## Context

Dependency injection frameworks can leak into business logic and make unit testing dependent on the DI container. `CLAUDE.md`: "Uber Fx is allowed only in composition roots and infrastructure module wiring." "Use constructor injection in domain/application code."

## Decision

Use ordinary Go constructors (`NewXxxService(deps...) *XxxService`) as the primary DI mechanism throughout `internal/application` and `internal/adapters`. Confine `go.uber.org/fx` to `internal/bootstrap/app.go` (the composition root, ~32 providers) and `cmd/api/main.go` (`bootstrap.New().Run()`, 7 lines).

## Consequences

### Positive
- Tests instantiate services directly with fakes — zero Fx involvement in the test suite (confirmed: no `fx.` references found in any `_test.go` file reviewed).
- The dependency graph is explicit and readable in one file (`bootstrap/app.go`) rather than scattered via struct tags or reflection-heavy magic elsewhere.
- Lifecycle hooks (`OnStart`/`OnStop`) give clean graceful-shutdown semantics — see [[Dependency Injection]].

### Negative
- All wiring changes require editing the single `bootstrap/app.go` file, which will grow as more services are added (already ~32 providers for the current 10-module scope).

### Risks
- If `cmd/worker` (see [[Background Jobs]]) is added later, its own composition root needs the same discipline — the boundary isn't automatically enforced, only established as a convention shared by the existing composition root.
