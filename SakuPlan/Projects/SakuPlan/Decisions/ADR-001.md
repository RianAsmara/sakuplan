# ADR-001: Fiber v3 as HTTP framework

## Status

Accepted

## Context

The backend needs a fast, low-overhead HTTP router for a Go modular monolith serving a mobile app and admin web client via a REST/JSON API. PRD §21 ("Initial Default Decisions") fixes the backend framework as Fiber v3, and `CLAUDE.md` makes it a hard rule ("Use Fiber v3 and Go 1.26.x").

## Decision

Use `github.com/gofiber/fiber/v3` (pinned `v3.4.0`) as the sole HTTP transport, confined to `internal/adapters/httpapi`. No other HTTP framework is used anywhere in the codebase.

## Consequences

### Positive
- Fast, low-allocation routing; minimal middleware stack (only `recover` + a custom request-context middleware are registered — see [[System Architecture]]).
- Fiber v3's `fiber.Ctx` interface keeps handler signatures simple and testable via `app.Test()`.

### Negative
- Fiber v3 is a comparatively young major version; API surface has already shifted once during this project (`fiber.Config.DisableStartupMessage` moved to `fiber.ListenConfig` between minor versions) — see [[Dependency Injection]] for the fix.
- Smaller middleware ecosystem than net/http-based frameworks — no off-the-shelf CORS/rate-limiting middleware is wired in yet (see [[Security Controls]]).

### Risks
- Future Fiber upgrades may require similar small API-surface fixes; there is no automated check pinning exact behavior beyond `go.sum`.
